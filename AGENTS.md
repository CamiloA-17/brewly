# AGENTS.md

Guide for coding agents (and humans) working on Brewly. It covers how changes reach GitHub,
how the system is built from the database up to the iOS app, and the conventions and pitfalls
that are easy to miss. Longer references live in `docs/` (`architecture.md`, `database.md`,
`api.md` and the ADRs in `docs/adr/`); keep them in sync when behavior changes.

## The project

Brewly is a native iOS social network for coffee lovers and baristas. Members register their
own **coffee beans** (farm, altitude, varietals, process, roast), pick the **brew methods** they
use from a global catalog, and write **recipes** - in Brewly a recipe *is* a preparation (dose,
water or beverage weight, ratio, grind, temperature, steps, results). They share recipes and
beans in **posts** with photos, follow each other, like, comment, save and remix recipes, and
get in-app notifications.

It is a Swift monorepo:

```
database/   PostgreSQL schema (dbmate migrations), dev seed, SQL tests
shared/     BrewlyShared Swift package, compiled by both the app and the server
server/     Vapor 4 API (BrewlyServer)
ios/        SwiftUI app: thin Xcode target + BrewlyKit Swift package with all the code
docs/       architecture, database, API docs and ADRs
scripts/    helper scripts used by CI and the Makefile
```

## Working with Git and GitHub

The repository belongs to one developer; agents act on their behalf.

- **Language.** Code, comments, SQL, docs, branch names, commit messages and pull requests are
  in English. The app's UI is English with a Spanish translation (see Localization).
- **Branches.** Create every branch from an up-to-date `main`, with one of these prefixes:
  `feature/`, `bugfix/`, `release/`, `hotfix/`, followed by lowercase words joined by hyphens
  (`feature/recipe-timer`). Don't use other prefixes, even if the environment suggests one.
- **Commits.** Conventional Commits: `<type>(<scope>): <imperative summary>`, with types
  `feat`, `fix`, `refactor`, `test`, `docs`, `chore`, `ci`, `perf` and scopes `database`,
  `shared`, `server`, `ios`, `docs` or a feature name. Explain the *why* in the body when it
  isn't obvious.
- **Authorship.** Commits are authored by the developer, not by the agent. Commit with the
  developer's git name and email (ask for them if the environment is configured with an agent
  identity), and add no attribution trailers such as `Co-Authored-By:` or session links.
- **Pull requests.** Open one only when the developer asks for it. The body has no line
  saying it was generated by an AI tool. Use this structure:
  - `## Summary` - what changes and why, in two or three sentences.
  - `## What's included` - grouped by layer (Database, Server, iOS, Docs).
  - `## How to test` - concrete steps with `make` targets and what to check in the app.
  - `## Checklist` - CI green, tests added, no credentials or secrets committed.
- **Before opening a PR,** CI must be green on the branch (jobs: database, shared, server,
  iOS). Push, wait for the run, and fix failures before asking for review.
- **No sensitive content in the repository.** No real credentials, no test accounts with
  passwords, no secrets, no personal data. Demo users use `@example.com` addresses and take
  their password from `DEMO_PASSWORD`; secrets live only in `.env` (git-ignored). Review the
  diff for this before pushing.
- **Stacked pull requests.** When a PR builds on another one, point it at the other branch
  and merge them in order, oldest first. Use "Create a merge commit" (squash rewrites the
  commits the next PR still contains) and delete each branch after merging, so GitHub retargets
  the next PR to `main`. If a branch is not deleted, the next PR merges into that branch instead
  of `main`: check each PR's base before merging.

## Architecture

### Database (`database/`)

PostgreSQL 17 (the schema also runs on 16), **SQL-first**: the migrations are the source of
truth, and neither the server nor an ORM creates tables. See `docs/database.md` for the ER
diagram.

- **Migrations** are dbmate files in `database/migrations/` named `YYYYMMDDHHMMSS_name.sql`,
  each with `-- migrate:up` and a working `-- migrate:down`; CI rolls everything back and
  migrates again. Never edit a merged migration; add a new one.
- **Conventions:** plural `snake_case` tables, `uuid` primary keys (`gen_random_uuid()`) for
  user data, `timestamptz` everywhere, `updated_at` kept by the `set_updated_at()` trigger,
  constraints named `<table>_<meaning>`, `COMMENT ON` for anything non-obvious, an index for
  every foreign key used in joins or cascades.
- **Enumerations** are DOMAINs (`visibility`, `roast_level`, `grind_size`) or CHECK constraints,
  mirrored by the enums in `shared/BrewlyShared/Sources/BrewlyCore/Models/Enumerations.swift`.
  Change both together.
- **Catalogs** (countries, varietals, processing methods, brew methods, grinders, flavor notes)
  are global reference data keyed by stable slugs or ISO codes, seeded by a migration with
  canonical English names; the app translates them.
- **Integrity lives in the schema:**
  - Composite foreign keys guarantee ownership: `recipes (bean_id, author_id)` references
    `coffee_beans (id, owner_id)`, and posts can only share their author's recipe or bean.
  - `recipes.ratio` and `recipes.extraction_yield_percent` are generated columns.
  - Deleting a bean used by a recipe fails; deleting a user cascades to everything they own
    (the App Store requires in-app account deletion).
  - `can_view_content(viewer, owner, visibility)` is the single rule for visibility: owners
    see their content, blocks hide everything in both directions, `public` is visible to all
    and `followers` to followers. `can_view_content(viewer, member, 'public')` doubles as the
    "no block between them" check.
- **Social tables:** `follows`, `user_blocks`, `posts`, `post_media`, `post_likes`, `comments`
  (replies one level deep), `recipe_saves`, `recipes.forked_from_id` (remixes), `notifications`
  (`notifications_once_idx` deduplicates follows, likes and saves) and `reports`.
- **Images** are JPEG bytes in the `media` table (at most 2 MB, 4096 × 4096), served by the API
  at `/v1/media/{id}`; `users.avatar_url` is generated from `avatar_media_id`. See ADR 0006.
- **Counts** (followers, likes, saves, remixes) are computed when read with indexed `count(*)`
  subqueries; there are no counter columns.
- **Tests:** `database/tests/NN_name.sql`, each wrapped in `BEGIN … ROLLBACK`, using the
  helpers in `_helpers.sql` (`expect_error`, `expect_equal`, `create_fixture_users`). Scope
  counts to fixture rows so the suite passes on an empty and on a seeded database.
- **Seed:** `database/seeds/dev_seed.sql` is development data only and must stay idempotent
  (running it twice changes nothing).

### Shared package (`shared/BrewlyShared`)

Compiled by the app and the server, so validation and API shapes are defined once.

- **`BrewlyCore`:** enums mirroring the database, `CalendarDate`, `BrewMath` (ratio and
  extraction yield, same formulas as the generated columns) and rules (`RecipeRules`,
  `BeanRules`, `AccountRules`, `PostRules`) that return structured `RuleViolation`s. The server
  renders them as English messages; the app localizes them.
- **`BrewlyAPI`:** request/response DTOs, `Page<T>` (opaque cursor), `APIErrorResponse` and the
  stable `APIErrorCode`s. JSON uses camelCase keys, snake_case enum values and ISO 8601 dates
  (`BrewlyJSON`).
- Tests use Swift Testing and run on Linux in CI.

### Server (`server/`)

Vapor 4, Swift 6. Fluent is used only for configuration and connection pooling: there are no
Fluent models or migrations.

- **Layers per feature** (`Sources/BrewlyServer/Features/<Feature>/`): a `Controller`
  (`RouteCollection`) → a `Service` (rules from `BrewlyCore`, 404 and field-error mapping) → a
  `Repository` protocol with a `Postgres…Repository` that writes explicit SQL through SQLKit.
  Features: Auth, Users (`/me`), Catalog, Beans, Recipes, People, Media, Posts, Notifications,
  Health. Routes are registered in `routes.swift`; everything except health and auth requires
  a bearer token (`req.userID`).
- **Core** (`Sources/BrewlyServer/Core/`): `AppConfig` (environment), `AppError`,
  `APIErrorMiddleware` (maps PostgreSQL unique / foreign-key / check violations to 409 / 409 /
  422), `PageCursor` (keyset pagination over `(created_at, id)`), JSON helpers.
- **Auth:** email and password (Bcrypt), 15-minute HS256 access JWTs and opaque refresh tokens
  (30 days, stored hashed, rotated on every use; reusing one revokes all sessions).
- **Writing SQL:** bind values with `\(bind:)`; decode rows into private `Decodable` structs with
  `decodeSnakeCase`; select `limit + 1` rows for keyset pages; write multi-statement changes in
  `database.transaction`; make toggles (follow, like, save) idempotent with
  `ON CONFLICT DO NOTHING` inside a CTE. Notifications are written in the same transaction as
  the action that causes them (`NotificationWriter` or a CTE).
- **Tests:** `Tests/BrewlyServerTests/UnitTests.swift` (services with hand-written fakes;
  `Unreachable…Repository` fakes must implement every protocol method) and
  `IntegrationTests.swift` (real PostgreSQL; skipped unless `TEST_DATABASE_URL` is set, needs a
  `JWT_SECRET` of at least 32 characters, truncates all user data before each test).

### iOS app (`ios/`)

SwiftUI, iOS 17+, Swift 6, MVVM + Clean Architecture. The Xcode project is generated by
XcodeGen from `ios/project.yml` and is not committed; the app target only holds `BrewlyApp.swift`
and assets. All code lives in the local package `ios/BrewlyKit`:

| Module | Contents |
|---|---|
| `BrewlyDomain` | Entities, drafts, repository protocols, use cases for operations with rules (`SaveRecipeUseCase`, `SaveBeanUseCase`, auth). Re-exports `BrewlyCore`. |
| `BrewlyNetworking` | `APIClient` (async/await; refreshes the token once on a 401), `Endpoint<Response>`, `Endpoints`. |
| `BrewlyData` | `API…Repository` implementations, DTO ↔ domain mapping, `SessionManager` (actor, single-flight refresh), Keychain token store, `APIImageLoader`, photo resizing (1600 px JPEG). |
| `BrewlyDesignSystem` | Colors (light and dark), `LoadState` / `AsyncContentView`, `Paginator`, shared rows and cards (`RecipeSummaryRow`, `PostCard`, `MemberRow`, `AvatarView`, `RemoteImage`), `AppRoute`, appearance setting, localization of enums and catalogs. |
| Features | `AuthFeature`, `FeedFeature`, `RecipesFeature`, `BeansFeature`, `MethodsFeature`, `ProfileFeature`, `PeopleFeature`, `NotificationsFeature`. Each exposes its root view and a `…Dependencies` struct. |
| `AppFeature` | Composition root: `AppContainer` builds the data layer and each feature's dependencies, `RootView` switches between sign-in and the tabs, route destinations. |

- **Dependency rule:** features import only `BrewlyDomain` and `BrewlyDesignSystem`, never
  `BrewlyData` or `BrewlyNetworking`, and never each other.
- **Navigation between features** uses `AppRoute` (`.member`, `.recipe`, `.post`,
  `.memberSearch`, `.followers`, `.following`, `.notifications`) with
  `NavigationLink(value:)`. `AppFeature` decides which view each route opens, and every tab's
  `NavigationStack` root calls `.appRouteDestinations()` once.
- **View models** are `@MainActor @Observable` classes that expose `LoadState`; paginated lists
  use `Paginator`. Likes, follows and saves update optimistically and revert on failure.
- **Images** come from the API with the access token: use `RemoteImage` / `AvatarView`, not
  `AsyncImage`. Media URLs are relative to the API base URL.
- **API base URL** comes from `Info.plist` (`BREWLY_API_BASE_URL` in `project.yml`:
  `http://localhost:8080` in Debug).
- **Tests** use Swift Testing with hand-written fakes per test target; there is no shared test
  support module, so a new protocol method means updating the fakes in every target that
  conforms to it.

### Localization

English is the development language; every module with UI has `Resources/Localizable.xcstrings`
with Spanish translations. Views use `Text("…", bundle: .module)` and
`String(localized: "…", bundle: .module)`. Add the Spanish translation in the same change as
the English text, and use plural variations for counts ("%lld saves"). Catalog items arrive from
the API with canonical English names and are translated by `BrewlyDesignSystem` by slug;
countries are localized from their ISO code.

## Running and checking

Copy `.env.example` to `.env` and set `JWT_SECRET` (`openssl rand -base64 48`) and
`DEMO_PASSWORD`. Requirements: Docker, the `psql` client (`brew install libpq`), dbmate,
Swift 6, Xcode and XcodeGen.

| Command | What it does |
|---|---|
| `make db-up` | Start PostgreSQL in Docker and apply migrations |
| `make db-migrate` / `make db-rollback` | Apply pending migrations / roll back the latest |
| `make db-seed` | Load demo data (`ana@example.com`, `leo@example.com`, password from `DEMO_PASSWORD`) |
| `make db-test` | Run the SQL tests |
| `make shared-test` | Test the shared package |
| `make server-run` | Run the API on http://localhost:8080 |
| `make server-test` | Server tests (integration tests need `TEST_DATABASE_URL` and `JWT_SECRET`) |
| `make ios-project` | Generate `ios/Brewly.xcodeproj` |
| `make ios-test` | BrewlyKit tests on the newest iPhone simulator |

CI (`.github/workflows/ci.yml`) runs the same checks on every push and pull request: the
database job migrates, runs the SQL tests, rolls everything back, migrates again, loads the seed
and reruns the tests; the server job runs unit and integration tests against PostgreSQL;
the iOS job builds the app and runs the BrewlyKit tests. When a toolchain isn't available
locally (for example Swift on a Linux container), push and rely on CI.

## Adding a feature end to end

A typical change touches every layer, in this order:

1. **Migration** (new file) and SQL tests; update the seed if demo data helps.
2. **Shared:** enums, rules and DTOs, with tests.
3. **Server:** repository SQL, service rules, controller routes, `routes.swift`; unit tests with
   fakes and integration tests.
4. **iOS:** domain entity and repository protocol, endpoint, API repository and mapping,
   feature view model and view, wiring in `AppContainer`; view model tests; Spanish strings.
5. **Docs:** `docs/api.md` (endpoints, errors), `docs/database.md`, `docs/architecture.md`
   (modules, roadmap), and an ADR for decisions that are hard to reverse.

## Pitfalls that have already cost a CI run

- PostgreSQL has no implicit cast from `bigint`: Swift `Int` values are bound as `bigint`, so a
  function that takes `integer` (such as `left(text, int)`) fails with a bound `Int`. Cast in
  SQL (`$1::int`) or use a literal.
- Data-modifying CTEs don't see each other's rows: when a CTE inserts and the main query counts,
  add the CTE's row count, as the follow, like and save queries do.
- FluentKit also exports a `Page` type; write `BrewlyAPI.Page` on the server.
- Swift Testing exports a `Comment` type, which is why the domain entity is `PostComment`.
  Avoid domain names that clash with `Testing` (`Comment`, `Tag`, `Bug`, `Trait`).
- A throwing call inside `#expect` needs `try`, and the test function must be `throws`.
- Several `NavigationLink`s in one `List` row don't react separately; use separate rows, or a
  `ScrollView` for cards with several links and buttons (`PostCard`).
- Keep migrations reversible and the seed idempotent; CI checks both.

## Roadmap

1. Architecture and skeleton: auth, catalogs, beans, recipes *(done)*.
2. Social: profiles, follows, saves, remixes, posts with photos, feed, likes, comments,
   in-app notifications *(done)*. Next: push notifications with APNs.
3. Trust and safety: block and report in the UI (App Store Guideline 1.2), moderation queue.
4. More: Sign in with Apple, search with `pg_trgm`, guided brew timer, offline cache, more
   languages.
